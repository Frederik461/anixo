# ANIXO releases

ANIXO release assets are packaged for **Windows 10/11 x64**, **macOS 13+ Apple
Silicon (arm64)**, and **macOS 13+ Intel x86_64**. A separate macOS CI matrix
builds and tests both architectures on `macos-15` and `macos-15-intel` runners:
[run 44919795580](https://github.com/Frederik461/anixo/actions/runs/44919795580)
passed on both. This is CI validation, not a clean-machine Finder/Gatekeeper or
playback claim; see [TESTING.md](TESTING.md) for the evidence status.

Each release is named **ANIXO v<version>** and tagged `v<version>`. A release
contains these downloadable assets:

```text
Windows x64:
  ANIXO-Setup-v<version>.exe                    per-user installer (Inno Setup 6)
  ANIXO-Uninstaller-v<version>.exe              standalone guarded uninstaller
  ANIXO-Portable-v<version>.zip                 no-install portable copy
  ANIXO-Updater-windows-x64.exe                 standalone updater helper

macOS 13+ Apple Silicon:
  ANIXO-v<version>-macos-arm64.dmg               drag-and-drop ANIXO.app
  ANIXO-Uninstaller-v<version>-macos-arm64       standalone guarded uninstaller
  ANIXO-Updater-macos-arm64.zip                  standalone updater helper

macOS 13+ Intel x86_64:
  ANIXO-v<version>-macos-x86_64.dmg              drag-and-drop ANIXO.app
  ANIXO-Uninstaller-v<version>-macos-x86_64      standalone guarded uninstaller
  ANIXO-Updater-macos-x86_64.zip                 standalone updater helper

All platforms:
  SHA256SUMS.txt                                 SHA-256 checksums for every asset
  release-manifest.json                          updater feed with pinned assets
```

`build-report.txt` may be present in the build output as a diagnostic log; it is
not a release asset. Helpers are deliberately excluded from app-asset selection
so the updater can never install its own helper as the application.

## Channels and versioning

| Channel | Version pattern | Meaning |
| --- | --- | --- |
| Beta | `0.1.0-beta.6`, `0.1.0-beta.6`, … | Early release. Settings and data layout may still change; back up your data folder before updating. GitHub release is marked as a pre-release. |
| Stable | `0.1.0`, `0.2.0`, … | Recommended for everyday use. Marked as a full release. |

Versions follow `major.minor.patch` plus an optional `-beta.N` suffix. Asset
file names always use the exact version string after the `v`, for example
`ANIXO-Setup-v0.1.0-beta.6.exe`.

## Automatic updates and channels

The in-app Update Center (`U`, or Settings → Updates → Open update center) reads
`release-manifest.json` from this release (or a configured HTTPS feed URL) and
chooses assets by platform, architecture, and channel. Stable releases never
receive a beta manifest. The current version `0.1.0-beta.6` defaults to the beta
channel; a stable build defaults to stable.

`release-manifest.json` is generated by `packaging/make_release_manifest.py`
from the finished artifacts. Every asset entry records its HTTPS download URL,
byte size, SHA-256 digest, platform, architecture, and kind (`installer`,
`portable`, or `helper`). The updater rejects a manifest with a wrong schema,
invalid version/channel, non-HTTPS URL, missing digest, duplicate platform/arch
kind, or missing helper. If `update_public_key` is configured in Settings, the
manifest must also carry a valid OpenSSL signature (`manifest.signature`,
base64, `sha256` signed bytes); otherwise signature verification is reported as
skipped and the pinned per-asset digests remain mandatory.

Downloads are streamed to a staging directory and hash-checked before the
package is opened. A separate helper process then waits for ANIXO to exit,
backs up only the ANIXO-managed application files, applies the new installer /
portable ZIP / `.app` bundle, health-checks `--version`, and rolls back from the
backup on any failure. User data, settings, history, watchlist, playback
preferences, user-installed dependencies, shortcuts, and uninstall registration
are never removed by an update. Cancellation is available until installation
begins. Redacted update events go to the data directory's update log.

Manual installation remains supported: download the asset, verify it, then run
the installer or replace the portable folder / `.app` bundle.

## Verify a download

`SHA256SUMS.txt` contains one line per release asset in the form
`<sha256>  <file name>`.

Windows PowerShell:

```powershell
Get-FileHash .\ANIXO-Setup-v0.1.0-beta.6.exe -Algorithm SHA256
Get-Content .\SHA256SUMS.txt
```

macOS Terminal:

```sh
shasum -a 256 ANIXO-v0.1.0-beta.6-macos-arm64.dmg
cat SHA256SUMS.txt
```

The hashes must match exactly. Do not run an unverified download. The in-app
updater performs the equivalent check automatically against `release-manifest.json`
before it opens any package; `SHA256SUMS.txt` is the human-verifiable copy.

## Publishing with the ANIXO CLI (recommended)

From a clean checkout on the configured release branch, run:

```powershell
Anixo release beta      # 0.1.0-beta.6 → 0.1.0-beta.6
Anixo release stable    # 0.1.0-beta.N → 0.1.0; requires typing "stable"
```

Use `Anixo release check [tag]` to resume monitoring and verification after an
interrupted shell or workflow timeout, and `Anixo release history [limit]` to
review local tags and published GitHub Releases. Add `--timeout-minutes MINUTES`
to `beta`, `stable`, or `check` when a longer/shorter workflow wait is needed.

The release repository is taken from `release_repo` when configured, otherwise
from the configured Git remote. It is intentionally independent of the
updater's `update_repo`, which may point at a tester's fork.

Every publish asks for confirmation and runs preflight before changing files:
repository/remote, branch, clean work tree, pushed HEAD, local/remote tag,
`gh` authentication, workflow presence, required tools, full pytest suite,
Python compilation, manifest generation/parse round trip, dependency lock,
and discovered version references. It prints `PASSED`, `FAILED`, `UNKNOWN`, and
`NOT TESTED` instead of implying unrun checks succeeded. The CLI never stashes,
resets, discards user changes, creates an incomplete GitHub Release, bypasses
HTTPS allowlisting, overwrites tags, or re-tags after a workflow failure.

After confirmation, it updates every tracked version reference, commits
`Release v<version>`, pushes the configured branch and tag, waits for the exact
tag-triggered workflow run, reports failed jobs, and verifies the published tag,
version/channel, Windows/macOS assets, HTTPS asset URLs, manifest schema, and
SHA-256 agreement between GitHub, `release-manifest.json`, and `SHA256SUMS.txt`.
A successful run ends with `READY FOR ANIXO UPDATER TEST`; clean-machine,
Finder/Gatekeeper, and real-terminal update behaviour still require manual tests.

## Building a release (workflow reference)

The CLI performs the release steps below automatically. These details document
what the workflow and fallback manual process do.

Prerequisites on the build machines:

* Python 3.12 and uv for all jobs;
* PyInstaller (via `uv sync --group build`) for the app and standalone helpers;
* Inno Setup 6 for the Windows installer;
* `macos-15` (arm64) and `macos-15-intel` (x86_64) runners for both DMGs;
* optional Apple Developer credentials for signing/notarization.

None of these are needed by end users.

1. **Prepare the release.** `Anixo release beta` or `Anixo release stable`
   discovers and updates these references automatically. For a manual dry run,
   keep the version string consistent in:
   * `pyproject.toml` (`project.version` and the pinned dependency set),
   * `packaging/build_windows.ps1` (`$Version` default),
   * `installer/AnixoSetup.iss` (`MyAppVersion`, `OutputBaseFilename`,
     `VersionInfoProductVersion` / `VersionInfoVersion`),
   * `.github/workflows/release.yml` (`APP_VERSION` default),
   * `INSTALLATION.md`, `TESTING.md`, and this document.
   `anixo.spec` always builds `Anixo.exe`, so its name does not change.
2. **Refresh the lock file** if dependencies changed:

   ```powershell
   uv lock
   uv lock --check
   ```

3. **Build Windows locally** from the repository root:

   ```powershell
   powershell -ExecutionPolicy Bypass -File packaging\build_windows.ps1
   ```

   This syncs dependencies, runs pytest, builds the one-folder app, the
   standalone uninstaller, and a one-file validation executable, validates the
   builds, compiles the installer, builds the portable ZIP, and writes hashes
   plus `build-report.txt`. If Inno Setup is unavailable the step is reported
   as `SKIP`, not faked; never publish from a report containing `SKIP` or
   `FAIL`.

4. **Build macOS on an arm64 Mac or macOS 15 runner**:

   ```sh
   bash packaging/build_macos.sh 0.1.0-beta.6
   ```

   This runs tests, builds the console binary and standalone uninstaller,
   generates `anixo.icns`, assembles `ANIXO.app`, creates the DMG, and writes
   per-architecture checksums. If Apple credentials are present it signs and
   notarizes the distributed DMG; otherwise it produces an unsigned build and
   reports that clearly.

   The `macOS CI` workflow runs the same build on separate `macos-15` and
   `macos-15-intel` runners, validates architecture/resources/dynamic libraries
   and both uninstall modes, and uploads per-architecture reports and checksums.
   Only a passing job uploads its DMG; run 44919795580 passed on both runners.
   This does not replace real Finder, Gatekeeper, clean-machine, or playback
   testing, and no Apple signing/notarization secrets were configured in that
   run.

5. **Review the artifacts** and `build-report.txt`. Confirm the Windows and
   macOS hashes, then follow [TESTING.md](TESTING.md). Do not claim clean-machine
   or Intel Mac compatibility until those checks have actually been run.

6. **Publish**: the normal path is `Anixo release beta` or
   `Anixo release stable`, which commits the version bump, pushes the branch,
   pushes the tag, monitors the workflow, and verifies the result. The manual
   equivalent of only the tagging step is:

   ```powershell
   git tag v0.1.0-beta.6
   git push origin v0.1.0-beta.6
   ```

   The `Release ANIXO` workflow runs separate Windows and macOS jobs (the macOS
   job covers both architectures), builds standalone updater helpers, uploads
   per-OS artifacts, aggregates them, verifies that every expected asset is
   present, writes a final `SHA256SUMS.txt`, generates `release-manifest.json`
   with pinned HTTPS URLs and digests, and publishes the GitHub release as a
   pre-release when the version contains `-`. A manual `workflow_dispatch` run
   is also available; it uses the version configured in the workflow. To sign
   manifests, sign the canonical payload from
   `UpdateService._release_signature_payload()` with OpenSSL, add base64
   `signature` plus an optional `signature_key_id` to the manifest, and set
   `update_public_key` in Settings on test machines. Do not commit private keys
   or tokens.

## Signing and notarization

macOS signing is conditional on these repository secrets:

* `MACOS_SIGNING_IDENTITY`
* `APPLE_ID`
* `APPLE_APP_SPECIFIC_PASSWORD`
* `APPLE_TEAM_ID`

When only the signing identity is present, the app and DMG are signed but not
notarized. When all four are present, the distributed DMG is submitted to
notarytool and stapled. When none are present, the DMG is unsigned;
`TESTING.md` records the status of the current release. Windows builds are
currently unsigned apart from any publisher reputation SmartScreen may assign.

## Data safety

The Windows installer writes only program files, shortcuts, a small
`uninstall-paths.ini` beside the app (so custom path overrides can be replayed),
and the ownership manifest (`install-manifest-windows.json`) in the user data
folder. Settings, history, watchlist, progress, playback preferences, and API
configuration are never touched on install or update. Updates are staged and
verified before a separate helper swaps only ANIXO-owned program files; the old
files are backed up and restored if the new build fails its health check.

The standalone and OS-level uninstallers remove only components positively
identified as ANIXO-owned. Pre-existing software, shared system components,
other apps' files, and personal data are never removed silently. **Complete
removal** is available only through the in-app Settings flow and requires a
separate final confirmation before personal data is deleted.
